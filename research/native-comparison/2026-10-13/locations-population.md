# Native-versus-project comparison: locations and population

## Scope and reading rules

This comparison uses the native game folder supplied for this task, `D:/Games/Europa Universalis 5/Europa.Universalis.V.v1.2.5-0xdeadcode/game`, the mod at `repo/Extended Timeline`, the dated location records under `et-history-data/locations`, and the converter at `et-converter`. Native evidence below is cited relative to that named root with file and line numbers. The folder label is not treated as independent proof of the product build. I inspected the specified start files plus the corresponding definitions for goods, pop types, estates, building types, location ranks, town setups, institutions, road types and production methods. The inspected `in_game/setup` tree contained country setup files; the population baseline is in `main_menu/setup/start/06_pops.txt`.

A crucial distinction is that a value appearing in a native setup file demonstrates observed use, not a universal engine requirement. Converter behavior is separately identified from the game's vocabulary. The native start expresses a concrete location-by-location pop distribution. The project stores date-keyed history and the converter creates one snapshot, but some modeled values are never emitted and some outputs still inherit the native setup unchanged.

## Converter behavior versus engine requirements

The world model snapshots date-keyed history, filters IDs against the map cache, and resolves resources, rank/setup, buildings, institutions, roads, pops and market flags (`model.py:127-163`). Generation is narrower: `generate.py:98-103` creates files for pops, cities/buildings, institutions, roads and markets, while `:34-41,111-117` copies selected native setup files. This describes converter behavior, not universal engine requirements.

A source-backed `resource` survives parsing but disappears from generated files. Buildings are emitted only for recognized IDs, positive integer levels and a resolvable country owner. That ownership gate can omit ownerless monuments; it is a converter rule, not an established engine requirement.

Similarly, city rank and town setup are separate values. The data model can read them, but the city generator requires both. A settlement archaeological site, tell, monumental enclosure or village is not automatically a native town or city. The project needs an archaeological evidence layer that records permanence, area, residential coverage, chronology and uncertainty separately from the game rank. Only a conservative explicit mapping should set `city.rank`; a missing rank must remain a valid outcome.

The map cache is an identifier whitelist. The observed `ligurian_sea_location_1` entry proves that its 34,377 IDs are not an all-land count. A prehistoric point site cannot be assigned to a game location because its name resembles a modern place. Coordinate containment in the mod geometry, date-appropriate landscape and source uncertainty are required before assigning a location ID. Lack of a mapped site is unknown evidence, not proof of zero population.

## Priorities for prehistoric location and population research

The highest priority is local population evidence with method and uncertainty. Scalar weights describe composition, while `gen_pops.py` supplies totals from a 1337 cache, placeholder era factors and a median fallback. These defaults do not provide prehistoric estimates; regional models also need a separate allocation method before they can support game-location totals.

A new Çatalhöyük study offers an actionable methodological example: Kuijt and Marciniak estimate 600–800 residents in an average year during the Middle phase (6700–6500 cal BCE), combining revised residential-building distribution with building biographies, archaeology and ethnographic evidence. They challenge prior estimates of 3,500–10,000. This is not a ready-made province total. It is a bounded estimate for a specified mound and phase, suitable for the research layer until site geometry and game-location coverage are verified.

The next priority is separating settlement scale from economy and production. The same project documents six cereals and three pulses alongside nuts, fruits and gathering, and chemical sourcing identifies East Göllü Dağ and Nenezi Dağ for a sample of 42 obsidian artefacts from one structure. These findings can inform crop/material evidence but do not establish crop yield, extraction volume, trade routes, or a native production-method ID. The research records capture these facts with site-level scopes, ranges and limitations in `locations-population-research.yml`.

Resolve resource emission first, then define a dated population interface that avoids medieval fallback values. Prioritize site-specific estimates and an evidence rubric for settlement rank; map production only when activity evidence supports it. Monuments alone do not establish population or urban rank, and archaeological labels do not establish ethnicity, language, ruler, polity or religion.


The final review adds the published Çatalhöyük point (37.6664° N, 32.8257° E) from the plant-subsistence study. The obsidian record’s wide date range is expressly site context, not a directly dated sample interval. Neither record has a game location ID.
